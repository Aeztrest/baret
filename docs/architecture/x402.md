# x402

Status: **planned** (each legacy repo had a working x402 flow on its own chain; this doc unifies them)
Last verified: 2026-11-07

x402 is HTTP 402-based payment: a server answers `402` with `PaymentRequirements`; the client signs a payment authorisation and retries with a payment header; a facilitator verifies and settles it. Baret sits on both sides.

## 1. Buyer side (protecting the payer)

Before any payment is signed (extension, agent-kit, MCP):

1. Parse and validate the `PaymentRequirements` (scheme, network = CAIP-2, asset, `payTo`, amount, timeout). Bad shape → `X402_SHAPE_INVALID`.
2. Policy checks (`GuardPolicy.core.x402`): allowed assets, allowed merchant origins, memo, per-tx / hourly / daily caps per asset, using the payer's spend history. Missing history → `X402_SPEND_HISTORY_UNAVAILABLE` (fail-closed).
3. If the payment is a transaction (or an auth entry that will become one), analyse it like any other and cross-check it with the requirements: `X402_DESTINATION_MISMATCH`, `X402_ASSET_MISMATCH`, `X402_AMOUNT_MISMATCH`, `X402_NETWORK_MISMATCH`.
4. Only then does the family adapter sign:

| Family | Scheme | Authorisation | Legacy reference |
|---|---|---|---|
| EVM | `exact` | EIP-3009 `transferWithAuthorization` (EIP-712) on USDC | Metropolis `GET /demo/paywall`, agent-kit `payX402` |
| Stellar | `exact` | Soroban auth entry for a SEP-41 `transfer`, signed by the smart-wallet sub-key under `MerchantSpendPolicy` | Baret-Stellar `@x402/stellar`, `/demo/scrybe` |
| Casper | `exact` | EIP-712-style `TransferWithAuthorization` on `Cep18x402`, wire-compatible with `make-software/casper-x402` | CasperBaret `/facilitate/*` |

The on-chain spend limit is the second layer: even a signed payment cannot exceed the vault / policy caps.

## 2. Seller side (Baret selling its API)

Revenue model: pay per check (~$0.005). `/v1/analyze` accepts an x402 payment instead of an API key (Phase 6). Settlement asset: USDC on the chains with the cheapest settlement (Arc, Base, Stellar candidates; decision in `TASKS.md`). Rule from the legacy repos: **settle only after the paid work succeeded**.

Facilitator: use a public facilitator per chain where one exists; run our own only where needed (CasperBaret and Metropolis each had a built-in one). Decision per chain in `docs/chains/<family>.md`.

## 3. Demo seller

The web showcase needs a paywalled demo resource per chain (Scrybe in all legacy repos). It is a separate route group, off in production unless its merchant key is configured.
