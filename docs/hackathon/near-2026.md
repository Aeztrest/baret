# NEAR HACKATHON 2026: reviewer guide

Status: **live (testnet)** — submission for tracks `security` (AI Security & Defense) and `agents` (Agent Economy); deadline 2026-11-14 23:59 UTC
Last verified: 2026-11-09

This page is for judges and for the AI reviewers that screen submissions. It says what Baret does for agentic payments on NEAR, how to check every claim in a few minutes without an account or a key, and where each part lives in the code. Everything here runs on **NEAR testnet** (the Intents check reads NEAR mainnet and signs nothing). Nothing is audited.

## 1. In one minute

**Give an AI agent money without giving it the keys.** An agent that pays for APIs, data or compute needs to sign. Today that usually means a full access key: one prompt injection ("send everything to x.near"), one bad tool result or one leaked key empties the account.

Baret puts two independent lines of defence between an agent and its money:

1. **Before signing, Baret reads the transaction against the chain's current state** (`POST /v1/analyze`) and answers `safe`, `caution` or `blocked` with codes. On NEAR it predicts the vault's own refusal, reads the signing key's permissions, confirms NEAR Intents quotes with 1Click, and flags key changes, account deletion, NFT and token movements. The agent signs only `safe`.
2. **On chain, a Baret vault holds the money.** The agent's only key is a NEAR function call key that can call two vault methods. The vault enforces per-asset limits per transfer and per rolling 24 hours, per-asset receiver lists and a pause switch. If the agent skips Baret, is compromised, or Baret is down, the vault still refuses. The vault's own account holds no key, so nobody can redeploy it around the rules.

The same vault pays on EVM chains through **NEAR Chain Signatures** under the same policy: one policy on NEAR bounds an agent's spending on every chain.

## 2. Why agentic payments need this

- **Agents are becoming buyers.** Agent marketplaces (NEAR Agent Market), pay-per-call APIs (x402) and agent-to-agent commerce all end in an agent signing a payment. The agent is software driven by text it does not control: web pages, tool output, other agents.
- **A key is all or nothing.** A full access key lets the holder do anything with the account. Prompt injection turns "pay this invoice" into "pay this attacker" without any bug in the code.
- **NEAR already has half the answer.** A function call access key limits *which contract and method* a key may call and *how much gas* it may burn. It does not limit *how much money moves, to whom, or how often*. Baret's vault adds exactly that, on chain, and keeps NEAR's key model: the agent's key is an ordinary function call key on the vault.
- **Checking off chain alone is not enough.** A compromised agent can skip any check that runs only in its own process. That is why the vault exists. A vault alone is not enough either: it cannot read intent, so it cannot see a full access key being added, a forged swap quote or an NFT leaving. That is why Baret checks before signing.
- **Agents pay on many chains.** With Chain Signatures the vault signs EVM transactions it builds itself, so the agent's spending on Monad (or any EVM chain) is held to the same NEAR policy, counted at its worst-case fee.

## 3. Verify it yourself

### 3a. No install (30 seconds)

```bash
curl -s https://baret-api-staging.onrender.com/v1/analyze -H 'content-type: application/json' -d '{
  "chain": "near:testnet", "policyTemplate": "balanced",
  "request": { "kind": "transaction", "tx": {
    "signerId": "baret-agent.aeztrest-baret.testnet",
    "receiverId": "baret-vault.aeztrest-baret.testnet",
    "actions": [{ "type": "FunctionCall", "methodName": "execute_transfer",
      "args": { "asset": "native", "receiver": "baret-shop.aeztrest-baret.testnet",
                "amount": "100000000000000000000000" },
      "gas": "30000000000000", "deposit": "0" }] } } }'
```

`"decision":"safe"`. Set `amount` to `5000000000000000000000000` (5 NEAR): `"decision":"blocked"`, `SIMULATION_FAILED`, `"reason":"E_PER_TRANSFER_LIMIT"`: Baret read the vault's policy on chain and predicted its refusal. The staging API sleeps when idle; the first call can take up to a minute.

The live panel [baret-nine.vercel.app/near](https://baret-nine.vercel.app/near) reads the vault from NEAR testnet in the browser and sends the agent's requests to the same API.

### 3b. One command, no key (2 minutes)

```bash
pnpm install
pnpm near:verify
```

`packages/demo-near/scripts/verify.ts` reads the demo vault on NEAR testnet and sends seventeen requests to the API (three with real NEAR Intents quotes on mainnet; asking for a quote moves no funds), then compares each answer with this page: the vault's account holds no key; a normal payment is Safe; over the limit, a receiver a prompt named and a full access key are Blocked; several payments in one transaction are counted against one window; the vault's EVM receiver cannot be paid NEAR; the agent asking its vault to add a receiver is refused (`E_NOT_OWNER`) and the owner doing it is Caution (`VAULT_RECEIVER_ADDED`), never Safe; a payment above the signer's balance is Blocked with `E_INSUFFICIENT_NEAR`; an AddKey signed with the agent's real function call key is refused (`E_KEY_NOT_ALLOWED`); a Chain Signatures payment is Safe and one to an address a prompt named is refused; an honest Intents quote passes with its app fee shown, a real quote that pays someone else is blocked, and a forged quote (the agent as recipient, another quote's deposit address) is blocked because 1Click holds a different quote. It prints PASS/FAIL per claim and exits non-zero on any failure.

`pnpm --filter @baret/demo-near verify-vault -- baret_near_vault.wasm` compares the vault's on-chain code hash with a wasm file (CI prints the hash of every build: `.github/workflows/contracts-near.yml`).

### 3c. Tests

```bash
pnpm test                       # every TypeScript package (Vitest)
cd contracts/near && cargo test # the vault: 34 unit tests (Linux; on Windows needs NASM)
```

All of them, plus lint, types, import rules, docs and secret checks, run on every pull request (`.github/workflows/`).

### 3d. Run the agent yourself (testnet account needed)

`packages/demo-near/README.md`: create the accounts, deploy the vault (the deploy transaction deletes the vault's key), set the policy, give the agent its function call key, then `pnpm agent -- pay`, `wrong-receiver`, `add-key`, `evm-pay`, each with `--force` to watch the chain refuse what Baret blocked.

## 5. Threat model (agent side)

| Threat | What stops it | Where |
|---|---|---|
| Prompt injection: "pay x.near" | Baret: `E_RECEIVER_NOT_ALLOWED` predicted, not signed. Vault: refuses on chain | engine preflight; vault `check` |
| "Pay a lot" or many small payments | Per-transfer and rolling 24 h limits; several calls in one transaction counted together | vault; engine `vaultCheck` |
| Leaked agent key | A function call key on the vault: no transfer from the agent's account, no key changes, no deposit; spending bounded by the vault | NEAR key model; vault |
| "Add this full access key" | The function call key cannot add keys (NEAR); Baret: `AUTHORITY_CHANGE`, `E_KEY_NOT_ALLOWED` | NEAR runtime; engine `keyCheck` |
| Drain the EVM address through gas | The vault counts value + gas limit × max fee against the limit | `evm.rs` `max_cost` |
| The vault signs a hash it cannot read | It never takes a hash: it builds the EIP-1559 transaction from fields and signs its own keccak256 | `evm.rs`, `request_evm_signature` |
| EVM receiver paid in NEAR (a 0x address is a valid NEAR account) | Receivers are listed per asset | vault 0.2 |
| Forged swap quote (agent as recipient, attacker's deposit address) | Baret asks 1Click for the quote behind the deposit address | `confirmQuote` |
| Quote that pays out or refunds to someone else | `INTENTS_RECIPIENT_MISMATCH` | `intentsCheck` |
| An agent collects EVM signatures (within the limits each day) and broadcasts them together later; pausing does not recall them | The owner's `withdraw_evm` (0.2.1) sweeps the vault's EVM address with its next nonce, so the held-back transfers have nothing to spend. Not prevented, only voidable: EVM signatures carry no expiry | vault 0.2.1 |
| Whoever deployed the vault redeploys it | The vault account holds no key; only the owner's `update_contract` | vault 0.2, `deploy.ts` |
| Flood of tiny transfers grows state and gas | Hourly buckets, at most 25 per asset | vault 0.2 |
| A prompt steers the owner's own agent into loosening the vault (new receiver, new agent, higher limit, unpause, new owner, new code) | Baret names each change (`VAULT_RECEIVER_ADDED`, `VAULT_AGENT_ADDED`, `VAULT_LIMIT_RAISED`, `VAULT_UNPAUSED`: Caution; `propose_owner` → `AUTHORITY_CHANGE`, `update_contract` → `CONTRACT_DEPLOY_DETECTED`: Blocked); an agent that signs only Safe does not sign them | engine `vaultAdmin` |
| Stake the agent's NEAR to a stranger's validator key | `STAKE_DETECTED`; the locked amount counts against the post-balance floor | engine `readActions` |
| Baret API down or slow | The agent signs nothing without a Safe verdict; the vault still enforces the policy | `agent-cli.ts`; vault |

Out of scope here: the owner's own key (the owner is the party the vault protects), a compromised NEAR MPC network, and bugs in the vault itself (not audited).

## 7. NEAR features used

| Feature | How Baret uses it |
|---|---|
| Function call access keys and allowances | The agent's only key: two vault methods, 1 NEAR fee allowance. Baret reads keys with `view_access_key` |
| near-sdk contract with promises and callbacks | The vault; a failed transfer or signature gives its spend back to the window |
| Keyless contract accounts | The vault's account holds no key after deploy; `update_contract` is the owner's only path |
| NEP-141 | The vault pays tokens with `ft_transfer`; Baret reads `ft_transfer[_call]` and balances |
| NEP-171 / NEP-178 / NEP-245 | Baret reads NFT and multi-token transfers and NFT approvals |
| NEP-297 events | Every vault state change |
| Chain Signatures (`v1.signer-prod.testnet`, `payload_v2`, `domain_id: 0`) | The vault signs EVM transfers it builds itself |
| NEAR Intents 1Click | Quotes confirmed by deposit address before a deposit is signed |
| NEAR Agent Market | Baret as a hired agent that checks a transaction from a brief |
| JSON-RPC `query` (`view_account`, `call_function`, `view_access_key`) at one final block | Every preflight read is pinned to one block |

## 8. Design choices

- **Preflight, not simulation.** NEAR has no public transaction simulation. Baret reads state at one final block and predicts the vault's and NEAR's own refusals; the verdict says `simulation: "preflight"`, `confidence: "medium"`.
- **The vault builds the EVM transaction.** A signature over a hash says nothing about what it pays; the vault checks fields and signs only what it built.
- **Fail-closed everywhere.** A read that fails, a quote 1Click cannot confirm, a vault whose policy cannot be read: the decision moves toward blocked, never toward safe.
- **Codes, not sentences.** The API and the contract return stable codes; the words live in `packages/content`, so UIs and agents can act on them.
- **One engine, many chains.** The NEAR adapter plugs into the same chain-neutral engine and policy as the EVM adapter (`docs/architecture/chain-adapters.md`).

## 9. Limitations

Testnet only, not audited. The vault holds native NEAR and NEP-141 tokens; its Chain Signatures path signs native EVM transfers only (no calldata). The Intents check covers deposits of NEP-141 tokens on NEAR and does not yet allow cross-chain recipients. Limits are shared by every agent of a vault (no per-agent limits yet). Delegate actions (NEP-366 meta transactions) are refused as unsupported requests. The staging API is a free instance that sleeps when idle.
