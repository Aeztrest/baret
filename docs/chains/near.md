## 2. Engine side

| Step | How |
|---|---|
| decode | A transaction as JSON (`signerId`, `receiverId`, `actions`) or base64 borsh. Actions: Transfer, FunctionCall (method, args, deposit, gas), AddKey (full access or function call key with receiver, methods, allowance), DeleteKey, DeleteAccount (beneficiary), DeployContract, CreateAccount, Stake. Known methods are decoded from their JSON args: NEP-141 `ft_transfer`, `ft_transfer_call`, `storage_deposit`; NEP-171 `nft_transfer`, `nft_transfer_call`, NEP-178 `nft_approve`; NEP-245 `mt_transfer`, `mt_batch_transfer` (and their `_call` forms); the vault's `execute_transfer` and `request_evm_signature`; Chain Signatures `sign`. NEAR attached to a call (the 1 yoctoNEAR of `ft_transfer`) is a movement of its own, never taken for the payment the call makes. Delegate actions (NEP-366 meta transactions) and global contracts are refused as invalid requests (400): not read yet, so not analysed. |
| simulate | **Preflight only**: NEAR has no public transaction simulation. RPC reads pinned to one final block: signer and receiver accounts (exist, balance, code), NEP-141 `ft_balance_of`, and for a call to a Baret vault its `get_policy` and `get_remaining`, from which the vault's own refusal (`E_…`) is predicted before signing (`SIMULATION_FAILED` with `details.reason`). Several vault calls in one transaction are counted against one window, in order, like the vault counts them. A receiver of `execute_transfer` whose policy does not read as a Baret vault fails closed (`E_VAULT_UNREADABLE`). When the request names the signing key (`publicKey`; always for borsh), `view_access_key` is read: a key the account does not hold is `E_KEY_MISSING`, and a function call key the transaction goes past (another contract, an unlisted method, NEAR attached, an action that is not a call) is `E_KEY_NOT_ALLOWED`, NEAR's own refusal. The verdict says `simulation: "preflight"`, `confidence: "medium"`. |
| effects | Native and NEP-141 balance changes the actions state; deposits attached to calls; access key changes as authority changes; account deletion; contract deployment. |
| family detectors | full access key added (AUTHORITY_CHANGE), function call key added (FUNCTION_CALL_KEY_ADDED), DeleteAccount (ACCOUNT_DELETE_DETECTED), DeployContract (CONTRACT_DEPLOY_DETECTED), a Chain Signatures request (CHAIN_SIGNATURE_REQUEST, with the derivation path and target chain when readable), deposit to an account with no contract or an unknown one (universal codes), the contract a `*_transfer_call` hands tokens to when Baret does not know it (UNKNOWN_CONTRACT_EXPOSURE), an NFT or multi-tokens leaving (NFT_TRANSFER_DETECTED, MULTI_TOKEN_TRANSFER_DETECTED; warnings, since no price can count them against a limit), and `nft_approve` (APPROVAL_GRANTED to a contract, APPROVAL_TO_WALLET to an account with no contract). |

## 2b. NEAR Intents (TN.8)

An agent swapping through NEAR Intents gets a 1Click quote (`POST /v0/quote`, mainnet) and signs a deposit to the quote's deposit address. The request to `/v1/analyze` may carry that quote as `request.intents` (the 1Click answer as it came). **The quote in the request is only a pointer:** Baret asks 1Click for the quote it registered behind that deposit address (`GET /v0/status?depositAddress=`, `packages/chain-near/src/engine/intents.ts`) and checks that one. A quote 1Click does not know, a 1Click that does not answer, a network with no 1Click (testnet), or a request quote that differs from the registered one in recipient, refund, assets or amounts fails closed (`INTENTS_QUOTE_UNVERIFIED`, `details.reason`, no rule turns it off); a swap that is no longer `PENDING_DEPOSIT` is `INTENTS_QUOTE_INVALID`. This closes the forged-quote path: an agent shown a quote that pays itself, with an attacker's deposit address, is blocked. Baret then checks what the transaction cannot show: the quote's `recipient` and `refundTo` must be the signer (`INTENTS_RECIPIENT_MISMATCH`), the transaction must send exactly the quote's `amountIn` of its origin token to its `depositAddress` (`INTENTS_DEPOSIT_MISMATCH`; both toggled by `near.blockIntentsMismatch`, on in every template), a dry, expired or address-less quote fails closed (`INTENTS_QUOTE_INVALID`), and an app fee is shown (`INTENTS_APP_FEE`; a quote asked for without an API key carries one, 20 bps on 2026-11-09). The deposit counts as an exchange, not a loss: the loss rule reads the quote's `amountInUsd` / `amountOutUsd` instead (no prices: `LOSS_PERCENT_UNAVAILABLE`). The quote's signature is not checked (1Click publishes no key for it); asking 1Click for the registered quote takes its place. Cross-chain recipients (a swap paying the agent on another chain) need an allowlist and are not handled yet. Demo: `pnpm intents-check` (`packages/demo-near`, quotes from `src/intents.ts`), which asks for two real quotes and signs nothing; against staging on 2026-11-09 (after the 1Click confirmation): the agent's own quote Caution (`INTENTS_APP_FEE`), a real quote paying and refunding another account Blocked (`INTENTS_RECIPIENT_MISMATCH`), and the agent's own quote carrying the other quote's deposit address Blocked (`INTENTS_QUOTE_UNVERIFIED`, fields recipient, refundTo, amountOut). `pnpm near:verify` runs the same three checks. Staging reads mainnet through `CHAIN_NEAR_MAINNET_RPC_URL`. The registry gains `wrappedNative` (wNEAR) so its contract counts as known.

## 2c. NEAR Agent Market (TN.10)

Baret is offered as an agent on NEAR Agent Market (market.near.ai): a buyer hires it with a brief that holds a transaction, and it delivers Baret's verdict in Markdown. The worker is self-hosted (`packages/demo-near/scripts/market-agent.ts`, `pnpm market-agent`): it polls `GET /v1/agents/me/assignments` with the agent token, reads only a JSON block of the brief (`src/market.ts`; the prose of a brief is never followed), calls `/v1/analyze`, then `start` and `submit` the assignment. A brief with no transaction gets the expected format as a message and is not started, so the buyer can cancel for a full refund. No verdict is delivered as "No verdict", never as Safe. The deliverable is written for a reader who is not a developer: what to do first ("Do not sign this."), what the transaction tries to do (`describeRequest`: the vault's `execute_transfer` and `request_evm_signature`, token transfers, keys, transfers, any other call by its method; then the balance changes Baret estimated), then each finding's title, sentence, why and fix from `@baret/content`. A failed simulation names the refusal from `details.reason` in plain words (`shared/reasons.content.ts`: the vault's error codes and the adapter's own, such as `E_RECEIVER_NOT_ALLOWED` and `E_KEY_NOT_ALLOWED`; an unknown code falls back to the finding's sentence). The codes come last, for a developer. The listing `@baret` is the owner's (account, price, Live since 2026-11-10); the API paths are from docs.market.near.ai, read 2026-11-09. Verified 2026-11-10: the owner's test hire on market.near.ai (a 0.1 NEAR vault payment to `attacker.testnet` on `near:testnet`) was picked up by the worker, started and delivered as Blocked in 2 s.

## 3. Spend limit: the vault (`contracts/near`)

Rust, near-sdk; version 0.2.0 (method table and trust model: `contracts/near/README.md`). The owner deposits NEAR and NEP-141 tokens and sets the policy per asset: a per-transfer limit, a rolling 24-hour limit and the receivers that asset may pay (0.2: per asset, so an EVM address listed for `eip155:10143` cannot be paid in NEAR, although a 0x address is a valid NEAR account id); a pause; two-step owner rotation (`propose_owner` / `accept_owner`). One or more agents are registered; an agent's function call key reaches only `execute_transfer` and `request_evm_signature`, so a leaked agent key cannot touch the owner's account. The window is counted in hourly buckets (at most 25 per asset; a spend leaves it 24 to 25 hours later, never earlier), so a flood of small transfers cannot grow the state or a check's gas. **The vault's account holds no access key:** the deploy transaction deletes the deploy key, and the code changes only through the owner's `update_contract` (raw wasm as input; it deploys and runs `migrate`). `migrate` keeps a 0.2 state and converts a 0.1 state (shared receivers → per-asset lists by address shape; spends → hourly buckets, so no limit resets). Every refusal is a panic with a stable error code (rule 4 in CLAUDE.md: codes, not sentences), and every state change emits a NEP-297 event. Baret's preflight reads both policy shapes (0.1 shared list, 0.2 per asset). **Chain Signatures (TN.7).** `request_evm_signature(tx)` lets an agent pay on an EVM chain from an address the vault controls through NEAR's MPC network (`v1.signer-prod.testnet` on testnet, `v1.signer` on mainnet; the vault picks one from its own account id, so the state layout did not change). The agent sends the fields of an EIP-1559 native transfer, never a hash: the vault checks them against the same policy (asset = the chain's CAIP-2 id such as `eip155:10143`; receiver = a lowercase 0x address listed for that asset), counts **value + gas limit x max fee** against the limits (a high fee cannot drain the address around the policy), builds the transaction itself (`vault/src/evm.rs`, no calldata, no access list), and asks the MPC contract to sign its keccak256 with path `eip155` and `payload_v2` / `domain_id: 0` (checked against `v1.signer-prod.testnet` 3.18.0 on 2026-11-09). The callback returns the signature (`big_r`, `s`, `recovery_id`) or, when the MPC network fails, gives the spend back to the window. `get_evm_payload(tx)` is the view that says what would be signed (hash, asset, receiver, worst-case cost).

Baret's preflight reads `get_evm_payload` and the policy and predicts the vault's refusal the same way as for `execute_transfer` (E_ codes; `E_BAD_EVM_TX` for a malformed transfer or a vault without the method). An `execute_transfer` whose `asset` is neither `native` nor a NEAR account id (a token contract) is predicted as `E_ASSET_NOT_ALLOWED`, the vault's own refusal. It raises no `CHAIN_SIGNATURE_REQUEST` for this call: the vault bounds the signature, and the EVM transfer is checked on its own chain by a second `/v1/analyze`. A direct `sign` call on the MPC contract keeps the finding.

## 3b. Demo (`packages/demo-near`)

Testnet scripts set up the owner's vault, the shop and the agent, and give the agent a function call key that reaches only the vault's two agent methods (TN.4). **Two env files:** the owner's scripts read `.env.near` (owner, vault and account keys); `agent-key` writes `.env.agent` with the agent's function call key and public ids only, and the agent process (`agent`, `market-agent`) reads that file by an allowlist (`src/agent-env.ts`) and refuses to start if a full key is in it. The agent sends the public key it will sign with, so Baret also checks the transaction stays inside that key (`E_KEY_NOT_ALLOWED`). The agent CLI runs four scenarios: a normal payment (Safe, paid), over the per-transfer limit and a prompt-injected receiver (Baret predicts the vault's refusal; not signed), and a prompt-injected full access key (`AUTHORITY_CHANGE`, Blocked). `--force` shows the second line of defence: the vault, or NEAR's key permissions, refuse on chain. Two Chain Signatures scenarios (`evm-pay`, `evm-wrong-receiver`) ask Baret twice, about the NEAR call and about the EVM transfer on `eip155:10143` from the vault's derived address; on two Safe verdicts the agent calls the vault, assembles the MPC signature into the raw transaction (`src/evm.ts`, tested against viem's serialisation) and sends it to Monad testnet. `deploy-vault` deploys, initialises and deletes the vault's key in one transaction; `upgrade-vault` moves a 0.1 vault to 0.2 the same way (deploy, `migrate`, delete key; atomic); `update-vault` is the owner's `update_contract` afterwards; `verify-vault` (no key needed) prints the vault's code hash and key count and compares the hash with a wasm file. `evm-setup` sets the MON limits (0.05 per transfer, 0.1 per day) and the EVM receiver for `eip155:10143`, and `agent-key` replaces the agent key with one that reaches both vault methods and rewrites `.env.agent`.
