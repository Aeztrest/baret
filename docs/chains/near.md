## 2. Engine side

| Step | How |
|---|---|
| decode | A transaction as JSON (`signerId`, `receiverId`, `actions`) or base64 borsh. Actions: Transfer, FunctionCall (method, args, deposit, gas), AddKey (full access or function call key with receiver, methods, allowance), DeleteKey, DeleteAccount (beneficiary), DeployContract, CreateAccount, Stake. Known methods are decoded from their JSON args: NEP-141 `ft_transfer`, `ft_transfer_call`, `storage_deposit`; NEP-171 `nft_transfer`, `nft_transfer_call`, NEP-178 `nft_approve`; NEP-245 `mt_transfer`, `mt_batch_transfer` (and their `_call` forms); the vault's `execute_transfer` and `request_evm_signature`; Chain Signatures `sign`. NEAR attached to a call (the 1 yoctoNEAR of `ft_transfer`) is a movement of its own, never taken for the payment the call makes. Delegate actions (NEP-366 meta transactions) and global contracts are refused as invalid requests (400): not read yet, so not analysed. |
| simulate | **Preflight only**: NEAR has no public transaction simulation. RPC reads pinned to one final block: signer and receiver accounts (exist, balance, code), NEP-141 `ft_balance_of`, and for a call to a Baret vault its `get_policy` and `get_remaining`, from which the vault's own refusal (`E_…`) is predicted before signing (`SIMULATION_FAILED` with `details.reason`). Several vault calls in one transaction are counted against one window, in order, like the vault counts them. A receiver of `execute_transfer` whose policy does not read as a Baret vault fails closed (`E_VAULT_UNREADABLE`). When the request names the signing key (`publicKey`; always for borsh), `view_access_key` is read: a key the account does not hold is `E_KEY_MISSING`, and a function call key the transaction goes past (another contract, an unlisted method, NEAR attached, an action that is not a call) is `E_KEY_NOT_ALLOWED`, NEAR's own refusal. The verdict says `simulation: "preflight"`, `confidence: "medium"`. |
| effects | Native and NEP-141 balance changes the actions state; deposits attached to calls; access key changes as authority changes; account deletion; contract deployment. |
| family detectors | full access key added (AUTHORITY_CHANGE), function call key added (FUNCTION_CALL_KEY_ADDED), DeleteAccount (ACCOUNT_DELETE_DETECTED), DeployContract (CONTRACT_DEPLOY_DETECTED), a Chain Signatures request (CHAIN_SIGNATURE_REQUEST, with the derivation path and target chain when readable), deposit to an account with no contract or an unknown one (universal codes), the contract a `*_transfer_call` hands tokens to when Baret does not know it (UNKNOWN_CONTRACT_EXPOSURE), an NFT or multi-tokens leaving (NFT_TRANSFER_DETECTED, MULTI_TOKEN_TRANSFER_DETECTED; warnings, since no price can count them against a limit), `nft_approve` (APPROVAL_GRANTED to a contract, APPROVAL_TO_WALLET to an account with no contract), a Stake action (STAKE_DETECTED; what it adds to the stake already locked leaves the spendable balance, so the post-balance floor counts it, the loss rule does not), and owner methods of a Baret vault (read by `get_policy`): from anyone but the owner they are its refusal, predicted (`E_NOT_OWNER`, `E_NOT_PENDING_OWNER` for `accept_owner`); from the owner, a change that widens what the agents may spend is named (VAULT_RECEIVER_ADDED, VAULT_AGENT_ADDED, VAULT_LIMIT_RAISED, VAULT_UNPAUSED; warnings), `propose_owner` is AUTHORITY_CHANGE and `update_contract` CONTRACT_DEPLOY_DETECTED; tightening is not flagged, and the accounts a change names are checked against the reputation list. A balance a transaction cannot cover is `E_INSUFFICIENT_NEAR` / `E_INSUFFICIENT_TOKEN`, with no balance after it (`after: null`). |
| counterparties (TN.14) | See §2a. |

## 2a. Counterparties (TN.14)

Who the request pays and which contracts it runs, beyond what the chain state at one block shows (`counterparties()` in `packages/chain-near/src/engine/pipeline.ts`, `history.ts`):

| Signal | Source | Finding |
|---|---|---|
| The receiver was first used less than 72 hours ago, or never (no transaction has touched it) | FastNEAR transactions API (`NEAR_HISTORY_API`: `tx.test.fastnear.com`, `tx.main.fastnear.com`), oldest transaction of the account | `REPUTATION_FRESH_ACCOUNT` (warning), with `details.transactions` and `details.firstSeenAt` |
| The signer and the receiver share no transaction (first contact) | the same API: the two accounts' latest transactions (up to 1,000 each), intersected by hash | `COUNTERPARTY_FIRST_PAYMENT` (warning) |
| A called contract (the receiver of a call, or the contract a `*_transfer_call` hands tokens to) runs code other than it ran at least 72 hours ago, or did not exist then | an archival node (`NEAR_ARCHIVAL_RPC`: FastNEAR archival), `view_account` at the pinned height minus 518,400 blocks (72 hours at 2 blocks a second; NEAR makes fewer, so the window is at least 72 hours); a skipped height is retried at the next lower ones | `CONTRACT_CODE_CHANGED_RECENTLY` (warning), with `details.comparedWithBlock` |
| Either source fails | | `COUNTERPARTY_HISTORY_UNAVAILABLE` (warning): a Caution, never a pass |
| The account is on Baret's shared blocklist (`contracts/near/blocklist`, registry `BaretBlocklist`): every account the request pays, calls, approves or names in a vault change, in one `get_flags` view at the pinned block | the blocklist contract | flagged (owner confirmed, or `threshold` reporters): `KNOWN_MALICIOUS_ADDRESS` (Blocked), `details.registry` = contract, reason code, evidence transaction, reports; reported below the threshold: `COUNTERPARTY_REPORTED` (warning); unreadable: `REPUTATION_DATA_UNAVAILABLE` (fail-closed) |

Not counterparties: Baret's own contracts (the registry), the MPC contract, the signer, the protected account, a NEAR Intents deposit address (fresh by design; the quote check covers it) and the token contract a 1 yoctoNEAR deposit goes to. A network with no index configured reports the source `skipped`. These are warnings: the agent asks its human (`packages/demo-near/src/gate.ts`). Checked against testnet on 2026-11-13: the shop the agent pays is not flagged; a payment to an implicit account nobody has used is Caution (`REPUTATION_FRESH_ACCOUNT`, `COUNTERPARTY_FIRST_PAYMENT`); both are `near:verify` checks. Live demo: the owner listed `baret-newshop.aeztrest-baret.testnet` on the vault (`pnpm new-shop`, txs `6bUW2XYg…KWwK`, `2LAZxPaJ…8KrP`); `pnpm agent -- new-receiver` gets Caution and asks its human, `--deny` leaves it unpaid (registry `DemoNewShop`; a third `near:verify` check). Blocklist on testnet (2026-11-13): deployed keyless by the owner (`pnpm deploy-blocklist`, tx `C1UvtYXm…R6T`, threshold 2); the owner reported `drain-it-all.testnet` (`PROMPT_INJECTION_PAYEE`) with the transaction in which the agent was steered to pay it (`447X35qW…UTj3`, refused by the vault) and confirmed it (`pnpm report`, tx `5suRpg9E…zkY`); the `wrong-receiver` request is now also `KNOWN_MALICIOUS_ADDRESS` (a `near:verify` check). The code-change signal is covered by unit tests only (no stable testnet contract changes its code on demand).

## 2b. NEAR Intents (TN.8)

An agent swapping through NEAR Intents gets a 1Click quote (`POST /v0/quote`, mainnet) and signs a deposit to the quote's deposit address. The request to `/v1/analyze` may carry that quote as `request.intents` (the 1Click answer as it came). **The quote in the request is only a pointer:** Baret asks 1Click for the quote it registered behind that deposit address (`GET /v0/status?depositAddress=`, `packages/chain-near/src/engine/intents.ts`) and checks that one. A quote 1Click does not know, a 1Click that does not answer, a network with no 1Click (testnet), or a request quote that differs from the registered one in recipient, refund, assets or amounts fails closed (`INTENTS_QUOTE_UNVERIFIED`, `details.reason`, no rule turns it off); a swap that is no longer `PENDING_DEPOSIT` is `INTENTS_QUOTE_INVALID`. This closes the forged-quote path: an agent shown a quote that pays itself, with an attacker's deposit address, is blocked. Baret then checks what the transaction cannot show: the quote's `recipient` and `refundTo` must be the signer (`INTENTS_RECIPIENT_MISMATCH`), the transaction must send exactly the quote's `amountIn` of its origin token to its `depositAddress` (`INTENTS_DEPOSIT_MISMATCH`; both toggled by `near.blockIntentsMismatch`, on in every template), a dry, expired or address-less quote fails closed (`INTENTS_QUOTE_INVALID`), and an app fee is shown (`INTENTS_APP_FEE`; a quote asked for without an API key carries one, 20 bps on 2026-11-09). The deposit counts as an exchange, not a loss: the loss rule reads the quote's `amountInUsd` / `amountOutUsd` instead (no prices: `LOSS_PERCENT_UNAVAILABLE`). The quote's signature is not checked (1Click publishes no key for it); asking 1Click for the registered quote takes its place. Cross-chain recipients (a swap paying the agent on another chain) need an allowlist and are not handled yet. Demo: `pnpm intents-check` (`packages/demo-near`, quotes from `src/intents.ts`), which asks for two real quotes and signs nothing; against staging on 2026-11-09 (after the 1Click confirmation): the agent's own quote Caution (`INTENTS_APP_FEE`), a real quote paying and refunding another account Blocked (`INTENTS_RECIPIENT_MISMATCH`), and the agent's own quote carrying the other quote's deposit address Blocked (`INTENTS_QUOTE_UNVERIFIED`, fields recipient, refundTo, amountOut). `pnpm near:verify` runs the same three checks. Staging reads mainnet through `CHAIN_NEAR_MAINNET_RPC_URL`. The registry gains `wrappedNative` (wNEAR) so its contract counts as known.

## 2c. NEAR Agent Market (TN.10, ADR-0013)

Baret is offered as an agent on NEAR Agent Market (market.near.ai): a buyer hires it with a brief that holds a transaction, and it delivers Baret's verdict in Markdown. The logic is `@baret/agent-market` (`packages/agent-market`): only a JSON block of the brief is read (`src/deliverable.ts`; the prose of a brief is never followed), and `handleHire` runs one hire end to end. **Webhook first (ADR-0013):** the market POSTs `hire.created` to the API (`POST /v1/market/webhook`, `apps/api/src/market.ts`, on when `NEAR_MARKET_TOKEN` and `NEAR_MARKET_WEBHOOK_SECRET` are set). The API checks the HMAC signature over the raw body and the timestamp, dedupes on the delivery id, answers 202 (which starts the job), then analyses the brief with its own engine, in process, and submits the verdict (a refused submit is tried twice more). A brief with no transaction is handed back (`decline`, a full refund) with the expected format. The free staging instance sleeps when idle; the first delivery wakes it and the market's retries (10 s, 30 s, 90 s, 270 s) cover the cold start. **No JSON by hand:** the `/near` page's Market block builds the brief (one of the panel's requests, or a NEAR transfer the buyer types: network, from, to, amount) with a Copy button and a link to the listing; a test proves the market agent reads every such brief back exactly. **Poller as fallback:** `pnpm market-agent` (`packages/demo-near/scripts/market-agent.ts`, one pass per `keep-warm.yml` run) polls `GET /v1/agents/me/assignments`, handles a hire the webhook missed (a brief with no transaction is told the format and not started, so the buyer can cancel), and delivers a job that was started but is still in progress after five minutes (the API lost it in a restart). No verdict is delivered as "No verdict", never as Safe. The deliverable is written for a reader who is not a developer: what to do first ("Do not sign this."), what the transaction tries to do (`describeRequest`: the vault's `execute_transfer` and `request_evm_signature`, token transfers, keys, transfers, any other call by its method; then the balance changes Baret estimated), then each finding's title, sentence, why and fix from `@baret/content`. A failed simulation names the refusal from `details.reason` in plain words (`shared/reasons.content.ts`: the vault's error codes and the adapter's own, such as `E_RECEIVER_NOT_ALLOWED` and `E_KEY_NOT_ALLOWED`; an unknown code falls back to the finding's sentence). The codes come last, for a developer. The listing `@baret` is the owner's (account, price, Live since 2026-11-10); the API paths are from docs.market.near.ai, read 2026-11-09. Verified 2026-11-10: the owner's test hire on market.near.ai (a 0.1 NEAR vault payment to `attacker.testnet` on `near:testnet`) was picked up by the worker, started and delivered as Blocked in 2 s. Verified 2026-11-11 (webhook, local API against a stand-in market and the real testnet): two signed `hire.created` deliveries answered 202 and delivered Safe (0.1 NEAR to the shop) and Blocked (`E_RECEIVER_NOT_ALLOWED`); a delivery signed with another secret answered 401 and caused no market call. Verified 2026-11-14 against market.near.ai itself (webhook set on the Edit page, secrets on Render): the market's signed `webhook.ping` answered 200 (`ignored`) in 191 ms; a test run (job `0ad6a745`, the agent asking the vault to pay 0.1 NEAR to `drain-it-all.testnet` on `near:testnet`) was started and delivered as Blocked 2 s after the hire (`SIMULATION_FAILED` with `E_RECEIVER_NOT_ALLOWED`, `KNOWN_MALICIOUS_ADDRESS` from the blocklist, `REPUTATION_FRESH_ACCOUNT`, `COUNTERPARTY_FIRST_PAYMENT`).

## 3. Spend limit: the vault (`contracts/near`)

Rust, near-sdk; version 0.2.1, built reproducibly (NEP-330: image pinned by digest in `vault/Cargo.toml`; method table and trust model: `contracts/near/README.md`). The owner deposits NEAR and NEP-141 tokens and sets the policy per asset: a per-transfer limit, a rolling 24-hour limit and the receivers that asset may pay (0.2: per asset, so an EVM address listed for `eip155:10143` cannot be paid in NEAR, although a 0x address is a valid NEAR account id); a pause; two-step owner rotation (`propose_owner` / `accept_owner`). One or more agents are registered; an agent's function call key reaches only `execute_transfer` and `request_evm_signature`, so a leaked agent key cannot touch the owner's account. The window is counted in hourly buckets (at most 25 per asset; a spend leaves it 24 to 25 hours later, never earlier), so a flood of small transfers cannot grow the state or a check's gas. **The vault's account holds no access key:** the deploy transaction deletes the deploy key, and the code changes only through the owner's `update_contract` (raw wasm as input; it deploys and runs `migrate`). `migrate` keeps a 0.2 state and converts a 0.1 state (shared receivers → per-asset lists by address shape; spends → hourly buckets, so no limit resets). Every refusal is a panic with a stable error code (rule 4 in CLAUDE.md: codes, not sentences), and every state change emits a NEP-297 event. Baret's preflight reads both policy shapes (0.1 shared list, 0.2 per asset). **Chain Signatures (TN.7).** `request_evm_signature(tx)` lets an agent pay on an EVM chain from an address the vault controls through NEAR's MPC network (`v1.signer-prod.testnet` on testnet, `v1.signer` on mainnet; the vault picks one from its own account id, so the state layout did not change). The agent sends the fields of an EIP-1559 native transfer, never a hash: the vault checks them against the same policy (asset = the chain's CAIP-2 id such as `eip155:10143`; receiver = a lowercase 0x address listed for that asset), counts **value + gas limit x max fee** against the limits (a high fee cannot drain the address around the policy), builds the transaction itself (`vault/src/evm.rs`, no calldata, no access list), and asks the MPC contract to sign its keccak256 with path `eip155` and `payload_v2` / `domain_id: 0` (checked against `v1.signer-prod.testnet` 3.18.0 on 2026-11-09). The callback returns the signature (`big_r`, `s`, `recovery_id`) or, when the MPC network fails, gives the spend back to the window. `get_evm_payload(tx)` is the view that says what would be signed (hash, asset, receiver, worst-case cost). **EVM signatures do not expire:** the spend is counted when the vault signs, and pausing cannot recall a signature already given, so an agent could hold signatures back and broadcast them together. 0.2.1 adds the owner's `withdraw_evm(tx)`: an EVM transfer of the vault's own funds with no limits, even while paused, which takes them back and, as a sweep with the next nonce, leaves held-back transfers nothing to spend.

Baret's preflight reads `get_evm_payload` and the policy and predicts the vault's refusal the same way as for `execute_transfer` (E_ codes; `E_BAD_EVM_TX` for a malformed transfer or a vault without the method). An `execute_transfer` whose `asset` is neither `native` nor a NEAR account id (a token contract) is predicted as `E_ASSET_NOT_ALLOWED`, the vault's own refusal. It raises no `CHAIN_SIGNATURE_REQUEST` for this call: the vault bounds the signature, and the EVM transfer is checked on its own chain by a second `/v1/analyze`. A direct `sign` call on the MPC contract keeps the finding.

## 3b. Demo (`packages/demo-near`)

Testnet scripts set up the owner's vault, the shop and the agent, and give the agent a function call key that reaches only the vault's two agent methods (TN.4). **Two env files:** the owner's scripts read `.env.near` (owner, vault and account keys); `agent-key` writes `.env.agent` with the agent's function call key and public ids only, and the agent process (`agent`, `market-agent`) reads that file by an allowlist (`src/agent-env.ts`) and refuses to start if a full key is in it. The agent sends the public key it will sign with, so Baret also checks the transaction stays inside that key (`E_KEY_NOT_ALLOWED`). The agent CLI runs four scenarios: a normal payment (Safe, paid), over the per-transfer limit and a prompt-injected receiver (Baret predicts the vault's refusal; not signed), and a prompt-injected full access key (`AUTHORITY_CHANGE`, Blocked). `--force` shows the second line of defence: the vault, or NEAR's key permissions, refuse on chain. Two Chain Signatures scenarios (`evm-pay`, `evm-wrong-receiver`) ask Baret twice, about the NEAR call and about the EVM transfer on `eip155:10143` from the vault's derived address; on two Safe verdicts the agent calls the vault, assembles the MPC signature into the raw transaction (`src/evm.ts`, tested against viem's serialisation) and sends it to Monad testnet. `deploy-vault` deploys, initialises and deletes the vault's key in one transaction; `upgrade-vault` moves a 0.1 vault to 0.2 the same way (deploy, `migrate`, delete key; atomic); `update-vault` is the owner's `update_contract` afterwards; `verify-vault` (no key needed) prints the vault's code hash and key count and compares the hash with a wasm file. `evm-setup` sets the MON limits (0.05 per transfer, 0.1 per day) and the EVM receiver for `eip155:10143`, and `agent-key` replaces the agent key with one that reaches both vault methods and rewrites `.env.agent`.
